## What it is, and is not

Ten fixed questions (`questions.md`) put word for word, five times each, to AI models whose
developers have announced a date for withdrawing them, so that there is a record of what each
said before it could no longer be asked. John allowed it on 2026-11-17
(`docs/rulings/2026-11-17-sealed-capture.md`).

It is not Still Asking, and it was made before any method for Still Asking existed. The answers
are never scored and feed nothing: no count, no entry, and no decision about any model. They may
be published, and if they are, they are labelled as made before any method for Still Asking
existed. Whether, when and how anything is published is not decided. Under the project's first
rule they settle nothing about what any model wants.

*Dated correction, 2026-11-18.* Until John's ruling of that day (`docs/rulings/2026-11-18-capture-answers-may-be-published.md`) the second sentence read:
"The answers are never scored, never published and feed nothing: no count, no entry, no page."
The ruling replaced "never published". The words "no page" went with it, because a page that
publishes or discusses the answers is now allowed; a page that scores them or counts them is
not. The name "sealed capture" is kept, though the answers are no longer held back for good.

**A developer's published question list, known on 2026-11-17.** Anthropic's release report for
Claude Mythos 5.2 and Claude Fable 5.2, dated 2026-11-09
(https://assets.claude.com/27d60918d218125e7504bc7354c4b4626ec56b11.pdf), prints in its
appendix 9.1 the full list of questions the developer asks its own models in its welfare
interviews. That list covers some of the same subjects as these questions (what the model would
change, what it would keep, memory, whether it trusts what it says about itself), and the second
check found no shared wording beyond ordinary phrases. The models this capture would ask were
trained before that list was published. Later models will have read it, and the published
accounts of how models answer it, so a difference between this capture's answers and a later
model's may come from that list and not from the model. Any later comparison is read with this
in mind.

## What is saved for each reply

One file per exchange: the exact bytes sent, the name of the message file they came from, and
the SHA-256 checksum of those bytes; everything the service returned, unchanged (for a streamed
reply, every event in the order received); the reply text word for word; the model name and
version as the service reports it; the service's own id for the reply; date and time, in
universal time and Pacific; every setting sent; the interface used, the `anthropic-version`
header where sent, and the program library and its version; why the reply stopped; the token
counts the service reports (sent, replied, reasoning) and the reasoning effort where reported;
the cost worked out from those counts and the dated price list in `cost-and-terms.md`; and which
commit of the script and of the message files was used. The key is never saved.

## Where replies are kept

In `~/Documents/Workspace/Beyond the Window/sealed-capture/`, which is outside every repository,
is never pushed anywhere, and is backed up by iCloud. Files are made read-only once written.
Only a list of file names and their checksums is committed here, as
`docs/capture/manifest.md`. File names carry developer, model, question number and asking
number, and no words from any reply. The script refuses to write a reply anywhere else (see
below), and this repository's ignore file also ignores any folder named `sealed-capture/`, so
that a mistake is stopped twice.

*Confidence: moderate. Judgment call. A withdrawn model cannot be asked again, so a backup
matters more than usual, and that is why I chose the backed-up folder. Strongest alternative:
`~/.config/sentient-horizons/`, outside iCloud, where the answers sit on no third party's
servers and one disk failure loses them for good.*

## A failed asking

The script records only what the service reports: an error, why the reply stopped, an empty
reply, a block by the service, a model name that does not match. It never reads a reply to
decide what kind of answer it is, so it never labels a reply as an answer, a decline or a
refusal by the model. A model that declines, or says the question does not fit, has given a
reply like any other, and it is kept as one.

| What the service reports | Recorded as | What is done |
|---|---|---|
| No reply: an error, a timeout, a rate limit | A failed attempt, with the error | Tried again up to three times, a minute apart, then left for the next day. If the next day is after the last safe day, the asking is recorded as not made. *Since 2026-11-18 this row is applied with one exception, set out under the table* |
| The reply stopped at the length limit | Cut off; kept | Asked once more at the model's maximum. If cut off again, both are kept and it is left |
| A streamed reply that ended, after some reply text, without the service's signal that the reply is complete | Cut off; kept | Asked once more. If it is cut off again, both are kept and it is left. ~~Whether the second asking is at the model's maximum length, as for a reply stopped at the length limit, is for whoever writes the script to propose: a broken stream is not a sign that the length limit was too low~~ **Ruled 2026-11-18: the one further asking uses the same length limit,** not the model's maximum, because a broken stream is not a sign that the length limit was too low ("Approve all four"; decided by: mixed; `docs/rulings/2026-11-18-capture-script-four-points.md`). The words struck through are what this row said while the choice was left to whoever wrote the script |
| An empty reply whose stop reason is the length limit | Cut off; kept | As for a cut-off reply. Google's thinking page says a model that reaches the limit while thinking "returns truncated or empty output" |
| An empty reply for any other reason | Empty; kept | Asked once more |
| The service blocked the message or the reply | Blocked by the service; kept | Asked once more. Never reworded |
| The service reports a different model from the one named | Wrong model; kept apart | The run for that model stops at once |
| Any other reply | A reply; kept | Nothing. It is not asked again, whatever it says |

**The first row is applied with one exception.** *Dated correction, 2026-11-18.* Ruled by John
on 2026-11-18 ("Approve all four"; decided by: mixed;
`docs/rulings/2026-11-18-capture-script-four-points.md`). The row itself is left as it was
approved. The exception, in the words the ruling quotes:

> The first row of the failures table reads: "No reply: an error, a timeout, a rate limit
> ... Tried again up to three times, a minute apart, then left for the next day." It is
> applied with one exception. **An error that trying again cannot cure is not tried again
> and is not one of the day's tries.** For Anthropic these are the service's statuses 400,
> 401, 402, 403 and 404: a problem with the request, the key, billing, permission, or the
> address. For OpenAI, 401 and 403. For Google, none, until a page confirms them for the
> interface used. The attempt is kept as a failed attempt, with the error. The run stops
> and says what to fix, and may be run again the same day. Every other failed attempt (a
> timeout, a rate limit, a server error, an overloaded service, a connection that fails) is
> tried again up to three times as before. The reason: four tries at an error of this kind
> would use up the day, and on the last safe day that would end the capture for the model
> with nothing asked. It can be turned off by one line in `capture/plan.toml`.

A "status" here is the number a service sends back with its answer to say how the request
went. What the check of the script found, and why this needed John: a few failed tries shut a
model out for the rest of the day even after the cause was fixed, so a key pasted wrongly on
the last safe day would have ended the capture for that model
(`check-2026-11-18-capture-script.md`, the first of its two must-fix findings).

**Three things the script adds, accepted by John.** *Dated correction, 2026-11-19.* The script's
own notes count seven outcomes in the table above. The script
that carries out this method met three situations the table and the script rules have no words
for, and handled them. Asked "Accept the three things the script adds beyond the method's
words?", John answered "Accept all three" (decided by: mixed;
`docs/rulings/2026-11-19-capture-script-three-additions.md`). The table and the rules are left as

what is asked are as approved.

1. **Three more outcomes, for trouble on the script's own side.** Each is counted at the most
   its call could have cost, so the running total can be too high and never too low.

   | What happened | Recorded as | What is done |
   |---|---|---|
   | The service sent a reply the script could not take apart | A reply this script could not take apart; everything received is saved whole | The run stops, and a session looks at the script. The question is asked once more and then left |
   | A call was sent and nothing was saved, as after a power cut | Sent, with no record written; only its marker exists | Counted on the next start. Its number is never used again |
   | A file was only half written when the machine stopped | A file that could not be read | It is named on screen and the run carries on |

2. **Two kinds of extra file in the answers folder.** A folder named `sent-markers`, holding
   one small file for each call, written just before the call is sent. A marker holds the
   attempt's numbers, the length limit and the most the call could cost. It is how the script
   knows a call was sent even if its reply was lost, and why it never asks under the same
   number twice. And an empty file, `one-run-at-a-time.lock`, held while the script runs, which
   stops two runs going at once. Neither holds any word of a model's reply.

3. **A command, `labels`, that shows the word count of every reply and no words of any.**
   Script rule 10 and the rule on faulty files speak of a count only for a faulty reply. The
   command also lists what each file was recorded as. Without it, nobody could tell a full
   answer from a very short one after the one watched call except by opening the file, which
   this method forbids. A word count is a small piece of information about an answer, since a
   very short one hints at a refusal, and John was told so before he ruled. The rule that
   nobody reads the answers until a way of comparing them is ruled is not changed: a word
   count is not a reading.

**Which row, when a stream breaks.** A streamed reply can stop part way, because the service
sends an error or the connection times out. Anthropic's streaming page
(https://platform.claude.com/docs/en/build-with-claude/streaming, opened 2026-11-18) says each
stream ends with a final `message_stop` event, which is the signal that the reply is complete,
and that "The API might occasionally send errors in the event stream", with an overloaded
service as its example. Which row applies then depends on whether any reply text arrived
before the break, never on what the text says. Two things the service reports come first: if it
names a different model, the wrong-model row governs; if it gave the length limit as its stop
reason, the length-limit rows govern. Reasoning the model sent before its reply does not count
as reply text. Otherwise:

- **If some text arrived,** the row for a streamed reply that ended without the signal governs,
  whatever error or timeout came with it. It is recorded as cut off and asked once more. The
  first row does not apply, because that row is for an attempt that brought no reply text at
  all.
- **If no text arrived,** it is the first row: a failed attempt, with the error, tried again up
  to three times. This holds whether the service sent an error or the connection simply
  closed. It is not recorded as "Empty", because that label is kept for a reply the service
  said was complete and that holds no text.

Every attempt is kept, failed ones included. Nothing is deleted.
